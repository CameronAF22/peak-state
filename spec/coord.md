# Coordination and spec (`coord`)

> Generated by `python3 tools/coord.py build` from coord/lanes.json and coord/decisions/. Do not edit by hand. The live view across every branch is the dashboard.

Run the protocol: lanes, the decision log, the generated spec, the dashboard, hooks and CI. Integrate lane branches into main and keep the board honest.

**Owns:** `README.md`, `LICENSE`, `.gitignore`, `CLAUDE.md`, `.claude/`, `.github/`, `coord/`, `tools/`, `site/`, `docs/`, `schemas/coord/`, `package.json`, `package-lock.json`, `tsconfig.base.json`  
**Depends on:** nothing  
**Brief:** [docs/hackathon/lanes/coord.md](../docs/hackathon/lanes/coord.md)

## Deliverables

- Coordination protocol, hooks and CI that make decisions and status mandatory
- Live dashboard on GitHub Pages plus an Artifact snapshot

- Integration of lane branches into main before the demo

## Decisions in force

### D-coord-001 · Repo is the coordination bus; tools/coord.py is the only writer

`accepted` · process · 2026-10-03 · [session](https://claude.ai/code/session_01QVbLwShgFGPq3zbXjnSGBK) · branch `claude/awesome-wright-ciik1f` · accepted by claude (coord)

**Decision.** Each lane works on its own branch. Coordination records (decisions, status, messages, session claims, events) are JSON files under coord/, one file per record so parallel branches never conflict, each validated against schemas/coord/. tools/coord.py writes them, renders the per-lane spec and trace, and reads coord/ from every remote branch with git ls-tree and cat-file so agents see each other without merging. Every lane-owned file must be covered by a decision's produces list, and every record names the session (id, URL, branch) that wrote it.

**Context.** Six Claude Code sessions will build the hackathon MVP in parallel and the user wants every decision logged, tied to what it produced, recoverable later, and visible in real time. Sessions run in separate containers and can only share state through GitHub.

**Alternatives considered.**

- One shared coordination branch every session pushes to: conflicts constantly and breaks the one-branch-per-session rule
- An external tracker (Linear, ClickUp, Notion): not tied to the code, and agents cannot enforce it in hooks
- The Artifact database as the bus: real time, but not versioned with the code and not readable from git or CI

**Consequences.** Messages arrive when the sender pushes, so latency is one push plus one fetch (hooks fetch at most every 90 s). Decisions are append-only; changes go through supersedes.

**Produces:** `coord/README.md`, `CLAUDE.md`, `schemas/coord/`, `tools/coord.py`, `tools/test_coord.py`

### D-coord-002 · Hooks and CI make the loop mandatory

`accepted` · process · 2026-10-03 · [session](https://claude.ai/code/session_01QVbLwShgFGPq3zbXjnSGBK) · branch `claude/awesome-wright-ciik1f` · accepted by claude (coord)

**Decision.** Project hooks in .claude/settings.json: SessionStart prints the board, inbox and loop; UserPromptSubmit fetches and announces new messages and stale status; PreToolUse blocks edits before a lane is claimed, edits to another lane's paths (unless borrowed) and hand edits to generated records; PreToolUse on git push rebuilds the spec and blocks until validation passes; Stop blocks once if the session changed files without its own decision, coverage, or a fresh status. GitHub Actions runs the unit tests and coord.py validate --base origin/main on every push and PR.

**Context.** The user asked for the protocol to be required, not advisory, and built into the repo as default hooks.

**Alternatives considered.**

- Instructions in CLAUDE.md only: agents drift under pressure
- Git pre-commit hooks: not installed by a fresh clone and invisible to the agent

**Consequences.** A coordination bug could block work, so every hook catches its own exceptions and allows the action; PEAK_COORD=off exists for a person debugging the tool.

**Produces:** `.claude/settings.json`, `.github/workflows/coord.yml`  
**Depends on:** D-coord-001

### D-coord-003 · Dashboard on GitHub Pages, rebuilt from every branch

`accepted` · technical · 2026-10-03 · [session](https://claude.ai/code/session_01QVbLwShgFGPq3zbXjnSGBK) · branch `claude/awesome-wright-ciik1f` · accepted by claude (coord)

**Decision.** The coord workflow rebuilds site/dashboard.html plus data.json from coord/ on every remote branch after each push (and every 15 minutes once on main) and force-pushes the result to the coord-dashboard branch. GitHub Pages serves that branch (Settings, Pages, Deploy from a branch, coord-dashboard, root). The same page, with the data inlined, is published as a claude.ai Artifact snapshot that coord republishes at each gate. The page polls data.json every 60 s.

**Context.** The user wants a shared dashboard (GitHub Pages or an Artifact) that shows lanes, decisions and status as they change. Pages deployments from non-default branches are restricted, and lane branches will not be merged until gates.

**Alternatives considered.**

- actions/deploy-pages: only deploys from the default branch, so nothing shows until merge
- Artifact only: cannot read the repo live without a GitHub connector the viewer may not have

**Consequences.** Pages needs a one-time setting by a repo admin. The dashboard lags a push by about one workflow run.

**Produces:** `site/dashboard.html`  
**Depends on:** D-coord-001

### D-coord-004 · Six lanes with exclusive path ownership

`accepted` · scope · 2026-10-03 · [session](https://claude.ai/code/session_01QVbLwShgFGPq3zbXjnSGBK) · branch `claude/awesome-wright-ciik1f` · accepted by claude (coord)

**Decision.** Lanes: coord, contracts, onboarding, sensing, reps, experience, as defined in coord/lanes.json. Each path belongs to exactly one lane by longest prefix. Contracts goes first so the other lanes build against fixtures. Each lane has a brief in docs/hackathon/lanes/.

**Context.** The MVP has four separable capabilities (onboarding, sensing, reps, app) plus shared contracts and coordination. Parallel agents need hard boundaries to avoid editing the same files.

**Alternatives considered.**

- Split by layer (frontend/backend): the demo is browser-only, so there is no backend to split off
- Fewer, larger lanes: less parallelism and harder ownership

**Consequences.** Cross-lane edits go through a message plus coord.py borrow. Human owners per lane are still open (humanOwner is null).

**Produces:** `coord/lanes.json`, `docs/hackathon/lanes/`  
**Depends on:** D-coord-001

**Decision.** Everything the demo needs runs in the browser. Lanes write TypeScript modules (onboarding/, sensing/, reps/) that the app in app/ imports through the types and API in contracts/. Profiles and rep logs persist locally in the browser. Network calls are allowed for the onboarding conversation model only, with a scripted fallback. **Context.** A hackathon demo has to run reliably on one laptop with possibly no network, and four lanes must integrate late without surprises.

**Consequences.** The Web Bluetooth strap path requires Chrome or Edge on desktop or Android.

### D-coord-007 · Detection inputs: simulator first, Web Bluetooth strap second, manual always

`accepted` · scope · 2026-10-03 · [session](https://claude.ai/code/session_01QVbLwShgFGPq3zbXjnSGBK) · branch `claude/awesome-wright-ciik1f` · accepted by claude (coord)

**Decision.** Sensing ships a deterministic simulator as the required input, a manual I'm-off trigger, and a Web Bluetooth Heart Rate Service adapter (HR plus RR intervals) as the stretch real sensor. Detection compares windows against the person's own calibration with a gate (consecutive windows, refractory period, optional sham rate). Oura stays context only. EEG and EDA are out of scope for the hackathon.

**Context.** docs/oura-constraints.md shows Oura cannot trigger in real time, and the On-Aim research plan (EEG plus EDA) is a ten-week study. The demo needs a signal that fires on cue.

**Alternatives considered.**

- Oura webhooks: minutes of latency, not a live trigger
- Webcam rPPG: fragile under demo lighting

**Consequences.** Without a strap on demo day the live path is the simulator, which must be honest on screen about being simulated.

**Produces:** `docs/hackathon/mvp.md`  
**Depends on:** D-coord-005

### D-coord-010 · Root npm workspace owned by coord; lanes are packages

`accepted` · technical · 2026-10-03 · [session](https://claude.ai/code/session_01QVbLwShgFGPq3zbXjnSGBK) · branch `claude/awesome-wright-ciik1f` · accepted by claude (coord)

**Decision.** coord owns the root package.json, package-lock.json and tsconfig.base.json. The root package.json declares npm workspaces contracts, onboarding, sensing, reps and app. Each lane owns its own <dir>/package.json and names its package @peak-state/<lane> (the app is @peak-state/app), extends ../tsconfig.base.json, and exposes test and typecheck scripts that the root runs with --workspaces --if-present. Lanes import each other by package name, never by relative path across lane folders. Changes to the root files go through a message to coord.

**Context.** contracts (M-20261003T140326Z-contracts-8c23, D-contracts-002) made contracts/ a package named @peak-state/contracts and asked who owns a root package.json, since no lane did and lanes could only import it by relative path.

**Alternatives considered.**

- Relative imports across lane folders: breaks when folders move and hides cross-lane coupling
- contracts owns the root package.json: every other lane would need contracts to add scripts and dependencies

**Consequences.** npm install at the root links all lanes. A lane without its package.json yet is simply skipped by --if-present scripts; npm install warns until every workspace folder has one.

**Produces:** `package.json`, `tsconfig.base.json`  
**Depends on:** D-coord-006

### D-coord-012 · Strategy model: ordered steps with submodalities; anchors are step detail; triad is derived

`accepted` · product · 2026-10-03 · [session](https://claude.ai/code/session_01QVbLwShgFGPq3zbXjnSGBK) · branch `claude/awesome-wright-ciik1f` · accepted by product owner (via coord)

**Decision.** A state's strategy is an ordered list of steps. Each step has a modality (visual, auditory or kinesthetic, plus other senses if offered), a direction (external or internal), the content in the person's words, and the submodalities from the playbook's core list (extended list optional). Song, scene and body anchors are stored as submodality detail on the matching step, and one step is marked as the anchor step. The contrast state's submodalities, the differences, and the drivers (the 1 to 3 differences with the largest rating change in the one-at-a-time test) are stored with the state as hypotheses with their measured deltas. The physiology, focus and language triad is a derived view (feeling steps to physiology, picture steps to focus, self-talk steps to language), never stored separately. Reps replay the person's own step order and speak the driver submodalities.

**Context.** The playbook elicits a strategy as an ordered sequence of represented steps (for example see something, say something to myself, feel it), where the order matters as much as the parts, and then the submodalities of each step. The product owner noted it maps onto Peak State's extraction session: the strategies are the sequence and the song, scene and body anchors are the submodality detail. Current lane plans assume fixed physiology, focus and language slots run in that order (D-contracts-003, D-reps-002).

**Alternatives considered.**

- Keep fixed triad slots and squeeze the sequence into them: loses the order, which the method says matters
- Store free text only: reps and detection cannot use it

**Consequences.** contracts redefines Profile v2 and the RepSession steps; reps supersedes D-reps-002's fixed order; sensing gets peak and contrast calibration windows from the playbook itself.

**Produces:** `docs/hackathon/elicitation-playbook.md`  
**Depends on:** D-coord-011
